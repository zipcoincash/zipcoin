# Draft: issue for github.com/ethereum/zkapi

Title: **Third-party funding of a note (adopt a deposit by commitment), and the 6.7M-gas deposit**

## Context

We are building "fund your zkAPI client from a Privacy Pools note": a user with a private ETH balance in 0xbow's canonical pool
(or another shielded pool) wants a zkAPI note whose deposit cannot be linked to their other activity. Today the only way is to
withdraw to a fresh address and let the client deposit from there, which works but costs a second transaction and leaves a
fresh-address → vault link on chain. The cleaner shape is one transaction: the shielded pool's withdrawal contract (a
"processooor") calls `ZkApiVault.deposit(commitment, amount, siblings)` with the user's commitment bound into the withdrawal
proof, so the vault deposit comes from a contract that funds many notes, not from any user's address.

`deposit` already allows this: it is payable, has no `msg.sender` restriction, and binds nothing to the caller. The pieces
missing are on the client side and in the gas bill.

## 1. Adopt a deposit by commitment (client/SDK)

Both clients create the pending deposit (`secret`, `registration_commitment`, `next_note_id`, `zero_path`) and expect the
*same* client to broadcast the deposit, then confirm it from the receipt (`confirmDeposit` requires
`pending.next_note_id == args.note_id`, and the browser store refuses a second active note). There is no way to:

- **export** a prepared deposit as `{commitment, amount}` (plus `next_note_id` / `zero_path` if the payer wants them) for an
  external payer, and
- **adopt** a `NoteDeposited(noteId, commitment, amount, expiryTs, root)` emitted for that commitment by *any* sender, at
  whatever `noteId` it landed on (slot conflicts move it), without a transaction hash from the client's own wallet.

Proposed:

- `zkapi-clientd fund --external` (and the SDK equivalent): prepare the note, print/return `commitment` and `amount`, and
  enter a "waiting for an external deposit" state that polls the indexer for `NoteDeposited` with that commitment, then runs
  the existing confirmation with the observed `note_id` / `expiry_ts`. The secret never leaves the client; the payer learns only
  the commitment, which is already public once deposited.
- Indexer: `GET /v1/notes/by-commitment/{commitment}` returning the deposit event (or 404), so adoption does not need log
  scanning from the client.
- A documented statement that `deposit` is intentionally caller-agnostic, so integrators can rely on it.

Security notes for the design: adoption must check `amount` equals the prepared amount (a payer depositing less would create a
smaller note; the client should refuse or warn), and the commitment must be unique per prepared note (the vault does not
reject duplicate commitments; a replay by the payer would create a second note the client cannot distinguish, so the client
should bind to the first `noteId` it adopts and ignore later ones).

## 2. The deposit costs ~6.74M gas, and it is the hash, not the tree

Every mainnet deposit so far burned 6,742,1xx gas. At 1 gwei that is ~0.0067 ETH (~$18) per deposit, against deposits of
0.0018 ETH (~$5); for a relayer or a processooor funding notes on behalf of users the gas dominates the fee, and for users
it is more than the credits they buy.

Where it goes, measured against the deployed library `Bn254Poseidon` at `0xc6B55e86668d8c446B3D81273AAb9CBb20F28c7f`:

| call | `eth_estimateGas` | net of the 21k base |
|---|---|---|
| `hash3(1,2,3)` | 127,555 | ~106k |
| `hash5(1,2,3,4,5)` | 179,884 | ~159k |

`deposit` runs `hash3PairPath32` (two hashes per level, old root and new root, 64 `hash3`) plus one `hash5` for the leaf:
64 × 106k + 159k ≈ 6.9M, which is the whole bill. The dual walk itself is already the minimum for a verified single-leaf
replacement, and it has to stay: the tree is not append-only (`mutualClose`, escape and `claimExpired` zero a leaf,
`challengeEscapeWithdrawal` restores one), so a cached right-frontier cannot stand in for the old-path verification. The
lever is the hash implementation:

- `hash3` is Poseidon with t=4 (3 inputs + capacity), `hash5` is t=6. `bytes internal constant ROUND_CONSTANTS` (6,240 bytes)
  is copied into memory on every call (`bytes memory constants = ROUND_CONSTANTS;`) and read back with bounds-checked
  `mload`s inside a generic `_permute` loop. Fully unrolled implementations of the same widths, with the constants as
  immediates, measured the same way (`eth_estimateGas` of an external call, net of the 21k base, anvil):

  | | `Bn254Poseidon` (deployed) | poseidon-solidity 0.0.5 | circomlibjs-generated bytecode |
  |---|---|---|---|
  | t=4, 3 inputs (`hash3`) | ~106k | ~78k | **~46k** |
  | t=6, 5 inputs (`hash5`) | ~159k | ~170k | **~98k** |

  Generating the same kind of unrolled code from *your* round constants and MDS (the vault's constants differ from
  circomlib's; the empty-tree root does not match a circomlib Poseidon, so this is a code-generation change, not a
  library swap) keeps every output identical by construction, which the existing test vectors would confirm.
- Estimated deposit cost after the port: 64 × ~46k + ~98k ≈ **3.0M gas, a ~2.3× cut** (from ~6.74M). `mutualClose`,
  escape initiation, challenge and `claimExpired` each run one `hash3PairPath32` too, so they drop by the same ratio.
  Nothing in the circuits, the SDK, the indexer, or the leaf and node formats changes.
- The library is linked into the vault bytecode, so the swap lands with the next vault deployment rather than in place;
  worth doing before the next fresh deployment or TVL cap change.

Two further options that compound with it, for later:

- **Batched deposits.** `depositMany(commitments[], amounts[])` from one caller shares the upper levels of the path, so a
  processooor or relayer funding several notes per block amortises most of the walk.
- **Validity-proof updates.** Have the depositor supply a Groth16 proof of the root transition for one or many insertions
  and verify it on chain (~250k gas), as the withdrawal path already proves membership. Largest change; makes deposits
  cheaper than today's closes.

Happy to send the generated Poseidon as a PR with a differential test against the current library (random inputs, both
implementations, equal outputs for `hash3`, `hash5` and `hash3PairPath32`) and a gas report, if the direction is agreeable.
